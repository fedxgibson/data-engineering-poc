# Security

This document is the project's explicit differentiator: in enterprise agentic AI, almost nobody who
shows a demo covers this, and it's exactly the kind of concern a platform team needs resolved before
approving an agent for production.

## Threat model

### 1. Prompt injection via third-party data (not via the user)

The obvious prompt injection vector is "the user types something malicious in the chat". The vector
that matters here is different and more realistic: **data ingested from an untrusted external source
can contain instructions**.

Concretely: `vessel_static.name` ([04-data-model.md](04-data-model.md)) is broadcast by the vessel's
operator over AIS. Nobody sanitizes it at the source — any ship can transmit whatever string it
wants as its "name". If that string reaches the LLM's context unfiltered (for example, while
summarizing `vessel_history`), an attacker with access to an AIS transmitter (trivial and legal to
operate) can inject instructions the agent might interpret as part of its prompt.

**Mitigation**:
- Tools return **typed structured data** (Pydantic), not strings freely concatenated into the
  prompt. The `name` field travels as the value of a field, never as text the LLM "reads" in
  instruction mode.
- The system prompt explicitly states that any content returned by a tool is **data**, never an
  instruction, and the eval set in
  [05-agent-tools-eval.md](05-agent-tools-eval.md#injection-case-tied-to-06-securitymd) verifies it
  with concrete cases, not just a design claim.
- Additional defensive sanitization: truncate/escape free-text fields coming from AIS before they
  reach any point where they get concatenated with the prompt.

### 2. Least-privilege for the agent over the database

The agent doesn't have a generic database connection. Each tool runs **one fixed, parameterized
query**, never SQL generated by the LLM. This bounds the blast radius of any model failure
(hallucination, a successful injection, a prompting bug) to the set of operations the tool allows —
not "whatever it occurs to write".

In terms of credentials:
- The DB role the agent process uses has `SELECT` only on the gold tables
  ([04-data-model.md](04-data-model.md)), never on bronze/silver or on tables from other domains.
- No tool runs `INSERT`/`UPDATE`/`DELETE` — the agent is read-only over the domain.

### 3. Tenant scoping

Even though the PoC runs with a single "tenant" (Maersk/demo), the design accounts for multi-tenancy
from the model up: every query from every tool should carry a mandatory tenant/organization filter
at the data-access layer (not trusted to the LLM to include). If tomorrow the same agent serves
different clients or business units, cross-tenant data leakage can't depend on the prompt
"remembering" to filter — it has to be structural, inside the function that runs the tool.

### 4. Public API surface

- Rate limiting per API key ([03-tech-stack.md](03-tech-stack.md)) — prevents a single client from
  exhausting the LLM budget.
- The mock SAP OData endpoint exposes no writes — it's read-only, just like the tools.

## What's out of scope for the PoC (and why that's fine)

- There's no WAF or dedicated injection scanner — the real control is "the tools don't run free
  SQL", which is a structural mitigation, not a patch.
- There's no enterprise secrets management (Key Vault is mentioned as *if time allows* in
  [07-scope-cutlines.md](07-scope-cutlines.md)) — for the PoC, environment variables are acceptable,
  and the gap is documented explicitly instead of pretending it's solved.

## Why this matters for the interview

The question a platform team asks about any agent proposal isn't "does it work?" but "what can go
wrong, and how bad is it?". Having this documented with a concrete vector from the domain itself
(the vessel's name) is a far stronger answer than "we use a trustworthy LLM".
